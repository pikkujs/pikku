# Virtual user run records are privileged, and reads sit behind a scope

`packages/core/src/wirings/virtual-user/virtual-user-run-store.ts` defines where runs and their findings are kept. Its SECURITY note says findings from an `adversarial` run are "working exploits carrying live ids", so the store is "a privileged store". The scaffold "gates every read behind a scope for that reason", and a host that exposes these records more widely "is publishing its own exploits" (`virtual-user-run-store.ts:101-105`).

The gate is generated by the CLI, not written in core. `packages/cli/src/functions/wirings/virtual-user/serialize-virtual-user-functions.ts` emits `scopes: ['virtualUser:read']` on `getVirtualUserRun` (line 393), `listVirtualUserRuns` (line 414), `getVirtualUserRunSteps` (line 435) and `listVirtualUserSchedules` (line 477). Starting a run is `scopes: ['virtualUser:run']` (line 328). The three scopes are declared by `defineScope` in the same file (lines 308-320), and `virtual-user-functions.test.ts` asserts each one (lines 53, 66, 149, 150).

The disposition that makes findings sensitive is defined in `virtual-user.types.ts`, where `adversarial` "probes authorization and tenancy; a 2xx can be the finding" (`virtual-user.types.ts:15`).

A virtual user cannot reach these RPCs through the catalogue, because the catalogue excludes any function whose scope starts with `virtualUser` (`virtual-user-derive.ts:38-46`).

**What this rules out:** exposing run records, and their transcripts, to any caller who holds the virtual user's scopes but not `virtualUser:read`, and a virtual user starting or reading runs through its own catalogue.
