Column constraints in `db/tables.ts` are real. `enum`, `min`, `max`, `minLength` and `maxLength` always reach the generated zod schema, the generated union types and `pikku meta db` / the console schema, and `pattern` reaches zod only. On Postgres and MySQL they also become named inline `CHECK`s on new tables, new columns and existing columns, and the introspectors read checks back on postgres, sqlite and MySQL. Check names are `<table>_<column>_<hash>_<kind>_check`, the hash being of the table and column pair so two tables never collide (MySQL keeps check names schema-wide); a name too long for the engine has its readable front cut and keeps the hash and the ending. The scheme is unreleased, so no deployed names change. MySQL checks are read back as a real MySQL 8.4 stores them (introducers, escapes), a `NOT ENFORCED` check is read as not enforcing, and MariaDB is refused before anything runs against it.

SQLite gets no generated `CHECK`: it cannot change one without rebuilding the table, so the constraints there are validation only. `pikku db generate` and `pikku db check` print one notice listing each declared constraint with the `CHECK` to add in a hand-written migration, suppressible with `validate.rules["db-sqlite-unenforced-constraints"] = "off"`. A `CHECK` written by hand in a sqlite migration is left alone and still types the column, and the notice leaves out any constraint such a check already enforces.

Adding, changing or removing a constraint on an existing Postgres or MySQL column is written instead of refused: `ADD`/`DROP CONSTRAINT` on postgres and `ADD CONSTRAINT`/`DROP CHECK` on MySQL 8.0.16+ (older servers are refused up front from the declaration), each added check carrying a `-- pikku:check-probe` line that `migrate` runs against the live rows first, through `checkProbeHook` (the MySQL probe is bounded by `max_execution_time`). `migrate` now refuses a pending migration marked `-- pikku:destructive` unless `allowDestructive` is given (`pikku db migrate --allowDestructive`, the standalone bundle's `db migrate --allow-destructive`); `pikku ci` passes it only when its worktree's database is its own (a SQLite file or embedded Postgres inside the worktree) or when `pikku ci --allowDestructive` says so; a worktree that points at a local server does not get it. On bun, `exec` now runs each sqlite statement on its own with a sqlite-specific splitter, because bun:sqlite drops a statement's error whenever anything follows it, which let a failed migration be recorded as applied.

A declared constraint is enforced at runtime only where a function uses the generated zod (`<Table>InsertZ`, `PatchZ`, `Z`) as its `input`; a Kysely write that skips such a function is guarded only by the DB `CHECK`s on Postgres and MySQL, and on SQLite not at all. Whole-number columns (`integer`, `bigint`, `smallint`, `serial`) are now generated as `z.number().int()`. When a declared `enum` differs from the enum the database holds, the generated union follows the declaration and codegen warns once per column (`PKU488`; on SQLite the advice is to add the `CHECK` by hand, since generate writes none there). A declaration that has both an `enum` and a `pattern`, or a numeric or text `default` its own min/max/length bounds reject, is refused when the file loads; this replaces the database silently winning.
