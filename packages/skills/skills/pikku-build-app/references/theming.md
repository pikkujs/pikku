# Authoring the theme

Read this at the design step, once you have a direction to turn into a theme —
whether the user described one in words, handed you a reference, or ran their own
design step whose output you are implementing.

Nothing in the open-source toolchain authors a theme for you. Fabric has the
`fabric-theme` tool; without it, hand-authoring is the route, and it is a small
job done in JSON.

## Where the look lives

```
packages/mantine-theme/
  themes/
    default.json     # "Neutral" — the shipped scaffold
    index.ts         # registers each theme JSON by id
  active.json        # { "id": "default" } — which one is live
  index.ts
```

Each theme JSON has two halves — `brand` (colours, fonts) and `structure`
(radius, shadows, spacing, per-component `defaultProps`). To give the product an
identity, add `themes/<name>.json`, register it in `themes/index.ts`, and point
`active.json` at its id.

`themes/index.ts` carries a `Generated by the fabric-theme tool — do not edit by
hand` banner. **That instruction is about Fabric's generator, not about you.**
Without that tool, hand-authoring is the only route, and the file is a three-line
registry. Edit it, and replace the banner with a line saying the themes here are
hand-authored — otherwise the next agent reads the warning and leaves the app on
Neutral.

Turning §1's answer into a theme:

- **Colour before anything else.** `brand.colors.primary` plus
  `structure.primaryShade` and `autoContrast` carry most of the identity;
  `@mantine/colors-generator` (already a dependency) expands one hex into a full
  scale.
- **Fonts are the other half of the register**, and the half people skip. A serif
  heading font against a neutral body is a different product from the system
  stack, and it is one field.
- **`structure.radius` and `structure.shadows` set the temperature.** Sharp
  corners and flat surfaces read technical; large radii and soft shadows read
  consumer. Neutral's `md: 10px` is the middle of the road on purpose.
- **`structure.components` defaultProps is where a design decision becomes
  automatic** — `Card` with `withBorder` everywhere, `NavLink` as `light`. Put
  the repeated decision here rather than on every instance.
- **`defaultColorScheme` and `darkColors` are a real choice**, not a toggle to
  leave alone. A tool people live in all day is often better dark by default.

Then **write the direction into `knowledge/decisions/design/`** — the words the
user gave you, what you chose, and what it rules out. The JSON records what the
theme is; only the note records why.

**Set the theme once, don't hardcode colours per component.** A screen full of
inline `color="blue"` and one-off hex values is why apps look templated. Change
the theme, not the components — and keep it theme-aware for light and dark.

With two apps, **share the theme package and vary the register, not the
palette.** A back-office can be denser and more tabular; a customer-facing app
can be roomier and warmer — that is `structure` and layout, not a second `brand`.
Two unrelated colour schemes read as two products from two companies.


## If the user gave you no direction

Neutral is a legitimate answer for an internal tool. But say so out loud when you
hand the work over — an unremarked default reads as a choice, and the user will
assume someone decided.
